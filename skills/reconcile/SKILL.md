# Reconcile

Refresh the trigger's normal authority scope and the authority scopes of its direct open dependents. Invoke this explicitly as `/reconcile <ticket-ref>` after the tracker reports that the triggering implementation ticket is resolved.

This is a tracker-state operation. Read the repository instructions and `docs/agents/issue-tracker.md` before any tracker write. Require that configuration to define the ready state, direct parent lookup, canonical blocker lookup, direct dependent discovery, affected reconciliation scopes, claim/assignment state, resolution state, child enumeration, and ready-state mutation. If any part is missing or ambiguous, stop and tell the user to migrate or re-run `/setup-skills`. The tracker's standalone authority mode matters only when resolving a parentless issue, as in step 3; parent-backed reconciliation never depends on it, even when that configuration is stale.

## Recompute the frontier

1. Resolve `<ticket-ref>` through the configured tracker and read its current state, parent reference, blockers, assignee or claim, labels/status, body with author metadata, and comments with author metadata and creation time as applicable.
2. If the ticket has a direct parent/spec reference or native parent, resolve that parent and read its approval and implementation children with their order. A present but unapproved, missing, or unresolvable parent fails closed and never falls back to standalone reconciliation. Neither a sibling nor a blocker supplies parent authority.
3. If the ticket has no parent, apply the same standalone authority mode as `/implement`. On a parent-only tracker (it states that standalone authority is unsupported, or that every implementation ticket has or requires a parent/spec), stop with a report that this tracker requires a parent/spec and make no mutations. On a tracker that still defines the retired standalone authority comment record (a `## Standalone implementation authority` comment), claims standalone support without the complete Agent Brief rule, states no mode, or states both modes, stop before any tracker write and tell the user to re-run `/setup-skills`. On a standalone-capable tracker, resolve its Agent Brief with the same Agent Brief resolver as `/implement`, as `docs/agents/issue-tracker.md` defines it: the newest complete trusted brief comment, otherwise the complete trusted issue-body brief, where trusted means a human author with effective `write` (including `maintain`) or `admin` repository permission and a failed permission lookup is untrusted. `author_association` is supplemental context only. The trigger's readiness label is not part of this check. If the trigger has no complete trusted brief, stop with a report and no mutations. Historical standalone authority comments grant no authority. For GitHub, paginate all issues in `state=all`, exclude pull requests, and read each candidate's parent relationships, issue author, and comments with author metadata. The standalone set contains every issue in the repository with no direct or native parent and a complete trusted Agent Brief from that same resolver, including closed issues so stale ready labels can be removed. Do not add unapproved or unresolvable parent issues to this set.
4. Verify the trigger is resolved according to the tracker. For GitHub, the issue must be closed. If it is open, stop without changing any ticket and report that post-merge closeout or the required close reference did not complete. Do not close it here.
5. Discover only the trigger's direct open downstream dependents using the configured canonical dependency representation. Native dependency data takes precedence over fallback text, including an empty native result. Use the configured fallback only when native data is unavailable. Discover by dependency references, independently of readiness labels or issue titles. Do not traverse dependents of discovered or newly promoted issues.
6. Resolve each dependent's own authority using steps 2 and 3 before selecting its scope. The trigger's approval never grants authority to a dependent. A parent-backed dependent selects all implementation children of its own approved parent, even when that parent differs from the trigger's. A parentless dependent selects the existing complete trusted standalone set. Report each authority failure and skip that dependent's scope; continue with independently validated scopes. An invalid trigger authority stops the entire run. Deduplicate scopes by parent identity or the standalone set before any write, keeping the trigger's scope first and processing dependents in configured deterministic order. Re-query all candidates in each validated scope, including closed issues so stale readiness can be removed. Repository enumeration for discovery or authority validation permits reads, not readiness mutation in unrelated scopes.
7. Classify each issue from current state in every selected scope:
   - ready when it is open, unblocked by every blocker, unclaimed or unassigned, and not held;
   - non-ready when it is blocked, claimed or assigned, closed, or otherwise non-executable;
   - held non-ready in both parent-backed and standalone scopes when it carries an explicit non-agent triage state: a label or status mapped from the `needs-triage`, `needs-info`, `ready-for-human`, or `wontfix` role in `docs/agents/triage-labels.md`. Reconciliation preserves that triage decision: it never promotes a held issue to ready and never changes its triage label. A held issue with a stale ready marker loses only that marker. An unlabelled planned issue carries no triage state and is promoted once its blockers close.
   Use native blocker relationships when available and the configured fallback only when native data is unavailable. An unresolved blocker reference cannot establish readiness.
8. Apply only the ready-state mutations needed to make every candidate match its classification, at most once per issue. An issue already in the correct state is a no-op. Reconciliation mutates readiness only and never creates or edits Agent Brief authority. Never modify parent resolution, dependency relationships, claims, issue resolution, or held triage states.
9. Preserve each parent's child ordering. Report a standalone frontier in ascending issue-number order. The frontier is every open, unblocked, unclaimed issue in that selected scope that is not held.

Report the triggering ticket, affected scopes, authority failures, promotions, removals, no-ops, unresolved blockers, and the resulting frontier for each validated scope. State explicitly when no mutations were needed. Re-running with unchanged tracker state must produce the same frontiers and no additional writes.

## Tracker branches

For GitHub, verify the merged PR's expected `Closes #<issue>` lifecycle indirectly through the issue's closed state. Fetch each candidate's issue author and comments with author identity, and accept an Agent Brief only from a human account whose current repository permission is effective `write` (including `maintain`) or `admin`, as defined by the tracker contract. Paginate the trigger's `dependencies/blocking` endpoint for direct dependent discovery and each candidate's `dependencies/blocked_by` endpoint for blocker classification, filtering dependents to open issues. If native reverse discovery is unavailable, paginate repository issues and invert each open issue's canonical blocker references, using fallback text only where its native blockers are unavailable. Exclude pull requests. Order direct dependents by issue number. If the trigger is still open, report the failed close-reference lifecycle and leave all dependents unchanged. Do not modify any parent spec.

For local markdown, resolve the supplied path or configured ticket identifier, follow its `Parent:` line, and verify its `Status:` is resolved or closed. Scan the configured issue files for exact `Blocked by:` references to the trigger, resolving identifiers in the containing feature and explicit paths across features. Resolve every dependent's own `Parent:` and rescan each selected spec's siblings in filename or configured parent order. Update only readiness fields needed to converge; preserve held, claimed, resolved, and closed lifecycle statuses. A local tracker that stores readiness solely in `Status:` cannot simultaneously carry a stale ready marker and a held or closed status. If local resolution already refreshed all affected scopes synchronously, a second run is a no-op.

## Scope boundary

Do not edit implementation code, commit, push, create or modify pull requests, close implementation issues, change parents, or execute downstream implementation. Mutate readiness only in the trigger's normal scope and scopes reached through its direct open dependents, retaining the full standalone set when selected. Merely transitive dependents do not select further scopes, though they may already belong to a selected scope. `/implement` still owns implementation, review, commit, and its configured handoff; `/reconcile` starts only after the tracker says that implementation ticket is resolved.
