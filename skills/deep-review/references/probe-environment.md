# Writable Probe Environment

The coordinator and writable validator apply this contract before accepting executable evidence. It applies to full reviews and follow-up revalidation. Static adjudication remains read-only and runs no setup or verification commands.

## Establish and hand off

1. After the static phase succeeds, restore, clean, and verify the exact recorded pinned baseline before every probe, including the first. Use only the existing authorization for that exact disposable worktree. Environment setup follows restoration, never precedes it.
2. Inspect the pinned target's tracked instructions, runtime/dependency declarations, applicable lockfile, dependency groups needed by the bounded check, and project-native setup/execution convention. Record paths and content identities, including declared runtime constraints. A plain manifest project may use its documented runtime's ordinary isolated installation without a manager or lockfile; record their absence. Neither require nor prohibit uv universally. Resolve instructions and declarations together; missing or ambiguous prerequisites are a specific limitation, not permission to guess a compatible environment or invent a lockfile.
3. Establish a run-owned dependency environment within the review's permitted disposable boundary. Name its absolute path, ownership and isolation basis, and writable locations for caches, temporary files, manager state, and build artifacts. Treat a caller/shared environment path as an inadmissible hint, not a validation input: do not inspect or execute that environment to establish staleness. Verify only the owned environment; runtime/tool discovery does not authorize access to a caller's application environment. Disable shared-environment inheritance or verify that it cannot affect the check. Use project-native commands with an explicitly selected environment and immutable/frozen dependency resolution where supported. Reject setup that changes dependency declarations or the lockfile, installs globally, writes through a link to a shared environment, or installs into, synchronizes, repairs, or otherwise mutates the caller or main checkout's environment. If the native convention cannot target the owned boundary within project instructions and inherited permissions, record the limitation instead of redirecting it into shared state. Only dependency acquisition required for this setup may use permitted package sources; this grants no application API calls or broader external access.
4. Supply exactly one hypothesis or original concern, its bounded question/check, and an **environment contract** to the writable validator. The contract names the pinned baseline, declaration/lockfile identities and selected groups, native convention and exact setup/execution commands, owned paths and effective access limits, actual runtime/environment to use, required dependency checks, code-origin check, and any known deviations or limitations. Supply this reference as a contract file. Either the coordinator or this one sequential validator may perform bounded setup/verification; the handoff records what has actually run and what remains to verify. The validator must not trust a pre-existing directory, a manifest declaration, an environment name, or an earlier invocation's verification as proof.

## Verify before executing the bounded check

Use the exact execution path the check will use, including any manager wrapper, selected dependency groups, working directory, and search-path settings. Capture the resolved executable/interpreter and its version, manager version when used, and installed dependency versions needed by the check. Compare the actual runtime and dependencies against the declared requirements and locked versions where applicable, including relevant transitive dependencies. Use native consistency checks where available and inspect installed metadata or equivalent runtime evidence; a successful setup command alone is insufficient.

Verify that production imports resolve and that the reviewed code is loaded from the pinned worktree, rather than an installed copy, the caller checkout, or a stale editable installation. For Python, inspect the actual interpreter, installed distribution versions, and imported module origins under that interpreter; do not bypass production imports to hide missing dependencies. For other runtimes, use their equivalent resolution/version checks. Record the verification commands, observed results, and comparison with the declarations. Detect stale environments, incompatible versions, and missing dependencies before accepting executable evidence. When verification cannot establish a match, do not execute the bounded check as though it had one.

## Substitutions and evidence limits

Never silently replace missing dependencies with mocks, stubs, fake modules, or import bypasses. Environment verification must succeed independently of substitutions. Legitimate mocking is permitted when the evidence explicitly names what is replaced, why the bounded question does not depend on it, and what the result cannot establish. A mock replacing behavior essential to the claim cannot support that claim. Preserve that limitation even when a command exits successfully; narrower evidence does not prove the broader hypothesis.

If setup or verification fails, preserve the attempted commands/results, specific limitation, remaining question, and needed confirmation. Never call the check passed or infer Finding/Disproved (or Addressed/Not addressed in follow-up) from failed execution. A completed validation attempt that cannot settle the question is Unresolved with evidence, Remaining question, and Needs confirmation; in follow-up it is Incomplete with Missing evidence. A hypothesis not attempted because of an operational failure is not validated due to review failure: mark the run incomplete, retain completed outcomes, block PASS, `No findings`, and publication, and name unattempted hypotheses. A validator crash, tool failure preventing adjudication, or restoration failure follows that operational failure path. Keep independently decisive static evidence usable with its actual provenance; a failed probe is never its supporting executable evidence.

## Preserve and restore

Before restoration, retain environment provenance and results in the invocation's entry in the consolidated run state, outside mutable probe state. Record:

- Reviewed base/head and exact restoration baseline; relevant manifest/lockfile paths and content hashes, selected dependency groups, runtime requirements, and absences or ambiguities.
- Environment location, ownership/isolation basis, owned writable/cache paths, resolved runtime and manager versions when used, exact setup and execution commands, relevant installed dependency versions, verification comparisons and code-origin results.
- Setup/verification/check results, any mock or other deviation with its justification and claim limits, remaining question/needed confirmation, and the actual outcome or operational failure.
- Restoration verification and environment disposal or invalidation, including exact leftover paths on failure. Preserve reproducible commands without credentials or other secrets.

Do not create a parallel environment ledger or per-probe evidence files without the protocol's concrete runtime-constraint exception. Evidence needed for repetition belongs in the run state before it can be erased. The coordinator then restores and cleans only the exact authorized worktree and verifies its baseline, tree, and status before the next sequential invocation. Also dispose of or invalidate every other owned mutable environment/cache location that could contaminate a later probe, using only scoped cleanup within the permitted run boundary. An environment removed by restoration must be re-established and verified before reuse; a retained environment must be verified again and any possible contamination eliminated before the next check. Failure to preserve required evidence or eliminate contamination stops validation as an incomplete run. This contract creates no broader caller access or reset/clean authorization.
