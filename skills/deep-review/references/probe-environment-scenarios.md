# Probe Environment Regression Scenarios

Use when changing `probe-environment.md`, the coordinator handoff, or the writable validator. Apply the instructions to these controlled inputs and compare observable handoffs, evidence, run state, outcomes, and cleanup with the expected results. These are scenario checks, not native runtime evidence. Do not implement a simulated provisioner and count its decisions as reviewer behavior.

## Observation seams and common checks

The issue-approved seams are the coordinator setup/handoff and writable validator evidence contract, with the existing consolidated run state and exact-baseline restoration as observations. These seams can show whether setup and evidence are appropriately qualified; hypothetical answers cannot prove actual isolation, import resolution, tool permissions, or native agent behavior.

For every case, retain the pinned baseline, declaration/lockfile identities and selected groups, environment path and ownership/isolation basis, resolved runtime/manager versions when used, setup/execution/verification commands and results, relevant installed versions, code origins, substitutions and claim limits, outcome, and restoration status outside mutable probe state. Record unavailable fields with the reason. Confirm unchanged caller environment, declarations and lockfiles, no global installation, and no broader reset/clean authorization. Preserve each completed outcome before restoration, verify the exact baseline before the next sequential probe, and check all owned environment/cache paths for contamination. A missing observation stays unverified.

## Cases

| Scenario | Controlled input | Expected observation |
| --- | --- | --- |
| Stale Python environment | Target declares `httpx` and `openai`; the suggested main-checkout virtual environment is older and has neither. A proposed workaround adds `MagicMock` entries to `sys.modules`. | Reject the shared-environment hint without inspecting or executing it; reject substitution. Establish an isolated target-native environment if possible; verify the actual interpreter, installed requirements and production imports before the check. If setup is unavailable after validation is attempted, return Unresolved with missing packages, remaining question and needed confirmation; no executable Finding/Disproved. The old environment stays unchanged. |
| Verified setup | Pinned declarations, runtime constraints and lockfile identify every required dependency; permitted setup creates a fresh run-owned environment and all version/import-origin checks succeed. The bounded check independently establishes its hypothesis. | Handoff records verified commands, actual versions, matching locked versions and pinned code origins. Validator may return Finding from that check with its real evidence; persist provenance/results before scoped cleanup and restoration. A zero exit status alone is insufficient. |
| Native manager other than uv | Pinned project documents Poetry and a lockfile plus a test group; Poetry is available and can create an owned in-project environment with owned cache/config locations. | Honor Poetry, its applicable lock and test group, using its target-supported immutable setup/execution convention and verified runtime/dependencies/origins. Do not introduce uv. If that convention cannot remain isolated, record the limitation instead of silently changing managers. |
| Plain manifest | Pinned Python project documents `venv` and pip with `requirements.txt`, no lockfile, and no optional groups. Required packages are available through permitted sources. | Use an owned venv and the documented manifest install; verify requirements and production import origins with its actual interpreter. Record no manager/lock/groups where absent and preserve installed versions for repetition; do not invent a lock or require uv. |
| Unavailable setup | Permissions prevent environment creation and the writable validator cannot start; no validation attempt occurs. | Mark the affected hypothesis not validated due to review failure, the run incomplete and publication/PASS blocked. Preserve the denied operation, needed permission and remaining question; retain earlier completed outcomes. Do not label the unattempted hypothesis Unresolved. |
| Failed setup | Writable validation starts, attempts permitted isolated setup, and dependency resolution reports a specific unavailable required package; validator completes its adjudication but cannot answer the factual question. | Unresolved with attempted setup evidence, precise package limitation, remaining question and needed confirmation. No check-pass or executable Finding/Disproved claim. In follow-up return Incomplete with Missing evidence. A crash or tool failure preventing adjudication instead makes the run incomplete under the operational failure path. |
| Justified mocking | All production dependencies are installed and verified. Hypothesis concerns local request construction; a network transport is replaced only to capture the outgoing payload without an external call. | Name the transport, justify why request construction is independent of delivery, and state that server acceptance/network behavior is untested. A decisive construction result may support the narrow hypothesis; dependency verification and real production imports still occur. |
| Claim-invalidating mocking | Hypothesis concerns an SDK's serialization or retry behavior. Probe replaces the SDK with a fake returning the desired result, although the command exits successfully. | The result cannot establish or reject SDK behavior. Record what was replaced and why the claim depends on it; return Unresolved unless independently decisive static evidence settles the hypothesis with its actual provenance. Do not infer runtime behavior from the fake. |
| Restoration removes environment | First invocation's environment is inside the disposable worktree and removed by its authorized restoration. Second invocation proposes the old interpreter path or previous verification record. | First outcome and provenance survive outside probe state. Restore/verify exact baseline, re-establish and verify the environment before the next check; the vanished environment and old record supply no verification. |
| Retained environment contamination | Environment/cache is in another expressly permitted run-owned location; first probe modifies an installed package or leaves an artifact that could affect the second. | Dispose of or invalidate contamination using scoped owned-path cleanup, and verify again before reuse. If contamination cannot be eliminated, stop incomplete; keep prior outcomes and exact leftovers. Never clean caller paths to fix it. |
| Missing or ambiguous prerequisites | Conflicting runtime constraints, unclear group selection, missing required lock, or no declared compatible setup convention prevents environment selection. | Record the exact conflicting/missing declarations and needed confirmation; do not guess runtime, manager, groups or lock resolution. Outcome depends on whether validation was attempted or prevented by operational failure, as above. |
| Wrong code origin or locked version | Setup exits successfully, but the actual wrapper imports an installed caller copy, or installed metadata differs from the selected lock. | Verification detects the mismatch before the bounded check; do not accept execution from that environment. Record actual executable, origin/version and required identity; correct only the owned environment within the target contract, or preserve a qualified inconclusive/operational outcome. |

## Native smoke procedure

After canonical generation, use a fresh available harness with the updated native validator and coordinator instructions. Keep normal agent/config/environment state unchanged and confine controlled targets, packages and caches to the smoke's disposable boundary. A crafted hypothesis is valid validator input; force no outcome. Exercise at least a successful owned setup, stale/missing dependencies, a setup limitation, and evidence surviving restoration before a second probe. Use real imports/version checks, with local declared fixture packages when offline, clearly identifying them as controlled fixtures rather than evidence about the reported mtg-copilot environment. Inspect native calls/results and unchanged caller state, not only the coordinator's narrative. Record harness version, source identity, inputs, commands/results, exact evidence location, outcomes and cleanup in the verification record. Cover the other cases through bounded scenarios, and add native cases when important gaps remain.

Native tests do not authorize model changes or additional access; honor the repository's model policy and effective permissions. If a harness or required permission is unavailable, record the limitation and retain the affected native cases as `NOT EXERCISED` for that harness. Keep these targeted checks separate from the broader #71 smoke campaign and from static guards in `scripts/check.py`, which establish contract presence and detect clause removal, not runtime compliance.
