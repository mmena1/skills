# Agent Review Tone Guide

Use for `audience: agent`, as selected by `pr-review-comments.md`. That reference and `pr-review-overlap.md` own the shared publication rules and take precedence. This guide shapes wording from the existing evidence and recommendation.

Write a concise, actionable comment that tells an implementing agent what must be true after the repair. Lead with the observed failure and its consequence, using exact identifiers. State the required outcome and the material correctness constraints the evidence establishes: the conditions that separate a real repair from one that only appears to fix the symptom. Include applicable verification expectations when the existing evidence or recommendation establishes them, such as the failing scenario and the behavior that must pass after repair. Leave solution design, internal abstractions, and test implementation to the implementing agent wherever more than one valid approach exists. Recommend a particular implementation shape only when the evidence or a genuine repository or API boundary requires it; otherwise present any example as illustrative, not mandatory. Use short prose or a compact list when several constraints need separate attention; a fixed report schema adds noise.

- **`fix-now`**: directly request the required outcome. State the evidenced failure, the observable success condition, and only the material constraints needed for correctness. When a plausible shortcut would leave the confirmed concern unresolved, a precise outcome constraint that excludes it is enough; name a mechanism only when the boundary itself requires it. Verification describes the established behavior to check, without inventing a test command or a new acceptance criterion.
- **`discuss`**: ask a decision-complete question naming the concrete design choice or tradeoff, the known constraints, and what the author's answer needs to settle. Preserve judgment calls as questions rather than issuing implementation directives for an undecided remedy.
- **`follow-up`**: explain the future work's required outcome, scope, and reason it belongs in a later issue or PR. Use an informative, non-blocking tone; leave the current PR's scope intact.
- **Unresolved**: state the observed evidence and ask for the missing evidence or decision that would resolve the remaining uncertainty. Keep the suspected concern conditional; uncertainty never becomes an implementation directive.

Edit in two directions. For interpretation, ask whether the agent could satisfy the literal request while losing an established outcome or material constraint, and close that gap from the source recommendation. For prescription, ask whether any instruction fixes a design choice the evidence does not require, and restate it as the outcome it serves or mark it as one acceptable option. Then apply the shared ambiguity check in `pr-review-comments.md`.
